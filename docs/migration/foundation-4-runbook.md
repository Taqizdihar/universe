# Foundation 4: offline inventory and first rehearsal runbook

The committed schema bundle at `database/schema-evidence/foundation-4/` contains only table metadata from the administrator's export. The local CLI uses no database client. It independently reproduces 19 Aiven tables, 28 Kroombox tables, 140 source columns, 48 source index parts, 62 column collation differences, two extra source `tenant_users` foreign keys, and nine target-only tables. **Current status: `no_go`.** All 24 source FK actions remain unknown; production row counts, identity decisions, and validation evidence are not present.

## Run the offline CLI

From repository root, run `node backend/migration/cli.cjs --out=/tmp/universe-foundation4-report.json`. The committed bundle is used by default. Use `--source=PATH --target=PATH --reference=PATH` for a revised local schema bundle. `--source-fk-actions=PATH`, `--source-counts=PATH`, `--target-counts=PATH`, `--evidence=PATH`, `--mapping-evidence=PATH`, and `--resolutions=PATH` are optional **local JSON files**; missing inputs keep the result `no_go`. The report contains only schema names, counts, finding codes, and evidence references. Keep operational evidence files and HMAC keys outside Git. Inspect a report before sharing it.

The source FK action JSON is an array of rows exported by the audit query, with `TABLE_NAME`, `CONSTRAINT_NAME`, `on_delete`, and `on_update`. The two count inventory files have `{ "environment": "aiven_v2" | "kroombox_development", "schema": "defaultdb" | "uniin_universe", "collectedAt": "2026-11-12T00:00:00Z", "counts": { "users": 0, ... } }`; include **every** table from the corresponding schema. These zeroes are format examples, not actual counts. The mapping-evidence file supplies `evidenceFile`, `evidenceSha256`, `collectedAt`, `administratorReviewStatus: "approved"`, and `mappedCounts` for every source table. A mapping count alone does not prove identities match; it is accompanied by the protected local decision file and the validation checks below.

Each evidence-manifest result supplies `checkId`, `sourceEnvironment: "aiven_v2"`, `targetEnvironment: "kroombox_rehearsal"`, `evidenceFile` (an existing local file), `evidenceSha256` (its SHA-256 digest), `collectedAt`, `status`, `findings`, and `administratorReviewStatus`. A `passed` result needs a nonempty JSON file matching its digest, a `checks` entry with the same `checkId`, `conclusion: "passed"`, and nonempty `observations`, no open findings, and administrator approval. The mapping-decision file needs a `checks` entry with `checkId: "identity_mapping_decisions"`. Required IDs are exported as `allChecks` from `backend/migration/evidence.js`: identity mapping, tenant memberships, API-key ownership, password-hash compatibility, legacy content round trip, publication status, Legacy API v1, media references, collation collisions, backup/rollback, source collation collisions, cross-environment collisions, and ordering behavior. A source-only zero collision count cannot satisfy the cross-environment check. The CLI does not accept `ignoreAllWarnings` or `forceReady`.

A redundant FK resolution may be supplied only as `{ "object": "tenant_users.tenant_users_ibfk_1", "code": "redundant_foreign_key", "decision": "accepted_redundant", "evidenceFile": "/protected/local/review.json", "evidenceSha256": "<64 hex characters>", "reviewedAt": "2026-11-12T00:00:00Z", "administratorReviewStatus": "approved" }`. Its nonempty JSON file must match the stated SHA-256 digest and list the object in `reviewedRedundantFks`; both source and target FK actions must be known and equal. The original finding remains in the report with `resolved: true`. This example does not approve the real FK; actual audit evidence is still missing.

## Administrator data collection

1. Confirm the selected servers and exact schema names. Use `database/audit/foundation-4/aiven-source.sql` only on the Aiven server's `defaultdb`, and `database/audit/foundation-4/kroombox-target.sql` only on the Kroombox server's `uniin_universe`. Both files explicitly qualify tables and filter `information_schema` by schema name; they do not rely on phpMyAdmin's breadcrumb or `DATABASE()`. **Read and verify the schema name before pressing Go.** They are SELECT-only and return exact aggregate counts, orphan/cross-tenant counts, duplicate-group counts, and FK actions; no raw email, key, password, or content rows are selected.
2. Store exports outside the repository. Convert FK action rows to local JSON without guessing absent actions. Record count inventories with collection time. Review errors and differences; a zero duplicate count on Aiven does not establish absence of cross-environment collisions.
3. When row-level matching is authorized, use a protected offline workflow and a secret HMAC key held outside Git. `fingerprintIdentity` and `compareFingerprintSets` in `backend/migration/fingerprints.js` support aggregate matching without emitting raw values. Use the same key and normalization rules in both environments, and protect both input inventories. HMAC comparison does **not** emulate MySQL collation; separately check database collation collisions and ordering.
4. Record source-to-target identity decisions and evidence for Super Admin preservation, password hashes, memberships, roles, API-key **value and ownership** preservation, page/post slugs and publication status, settings/footer, navigation, legacy JSON, CDN media references, and Legacy API v1. Do not copy auth verification tokens, regenerate API keys, rewrite media URLs, or infer identity from numeric IDs or emails alone.

## First isolated rehearsal

Provision a separate disposable database through the approved administration process. Verify source and target backups and restore paths; do not truncate the existing Kroombox development database. Review mappings, collation/uniqueness findings, dependency order, media plan, and every evidence result. A future operational SQL package must receive **separate administrator approval**; this phase provides no import DML. The human administrator alone executes reviewed DDL/DML through Kroombox phpMyAdmin in the disposable database.

After a future import, compare exact counts, orphan and cross-tenant counts, slug/uniqueness groups, Super Admin and role assignments, API-key ownership, password login compatibility, publication filtering, page/post content round trips, settings/footer/navigation, and CDN asset availability. Run Legacy API v1 contract and security tests against the isolated rehearsal backend. Keep Render-backed tenant websites on their current API base URL. API cutover, CDN migration, and future Content Schema Registry adoption are separate decisions.

Any missing FK action, unresolved duplicate FK, collation collision, incomplete identity map, missing evidence, failed API contract, or unavailable backup is **no-go**. Stop, retain the evidence, reconcile against the backup or discard the disposable database. Production cutover requires another explicit human decision after rehearsal; `ready_for_rehearsal` is not cutover authorization.
