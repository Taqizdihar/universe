# Foundation 5A: reviewed legacy exceptions and isolated rehearsal

Foundation 5A is offline and opt-in. It does not change startup, login, CRUD, CDN, SMTP, or Legacy API v1. Historical audit counts (about 33 users, 33 tenants, 46 memberships, 33 API-key records, 71 Pages, 120 Posts, 327 Media, and 1,505 rows overall) are **baselines**, not current inventories. Re-collect exact counts before a rehearsal. Current readiness remains **no-go** until FK actions, row inventories, identity decisions, and exception evidence are reviewed.

## Scoped legacy decisions

`backend/migration/decisions.js` accepts only named decision kinds. Each decision needs `decisionId`, `sourceEntity`, `sourceIds`, `workspaceId`, `findingType`, `action`, `schemaCollation`, `sourceSnapshotFingerprint`, `targetSnapshotFingerprint`, `evidenceFile`, `evidenceSha256`, `reviewedAt`, and `administratorReviewStatus: "approved"`. Slug decisions additionally bind `matchMode` (`exact` or `target_collation`). A protected local JSON evidence file must match its SHA-256 digest. It must contain a passing `checks` entry with the decision ID and nonempty observations, plus a `decisions` entry matching **all scope fields**. Existing-identity decisions also bind source/target email fingerprints and target user ID. Do not commit the evidence file, raw email matches, or actual record inventories. A stale snapshot, mismatched tenant/records/collation, or changed evidence file invalidates the decision. There is no generic waiver. `foundation-5a-decision-template.synthetic.json` illustrates the structure with fictional IDs and deliberately non-approved placeholder evidence; it cannot authorize an exception.

Post slug screening groups source records by tenant and exact slug or supplied 64-hex opaque target-collation key from a protected, reviewed MySQL-collation audit. A provisional Unicode normalization match is **never** enough to approve an exception; MySQL collation behavior needs administrator-exported evidence. Same-template published collisions always block. Cross-template published groups may receive a scoped `preserve_all_with_api_review` decision; published/draft groups may receive `preserve_all`. The verified Sentra Kreasi finding concerns 11 groups, with eight cross-template published pairs and three published/draft groups. Preserve all 23 affected Posts and their media. These facts are not hardcoded into public fixtures, and new collisions do not inherit the approval.

Legacy `GET /api/v1/public/posts/:slug` filters by tenant and slug, then uses `LIMIT 1` without deterministic ordering or a template filter. Preserving both records does **not** guarantee which one detail requests return. Before marking a cross-template pair reviewed for rehearsal, compare the published list containing both records, template-specific frontend usage, the detail record observed on the source, and the corresponding mapped record observed on rehearsal. Record a separate `legacy_api_ambiguity` decision with an explicit observed-detail policy. Do not claim `ORDER BY id` reproduces current behavior. Keep the v1 response shape and production endpoint unchanged; a future typed endpoint is a separate project.

An existing target Super Admin may be reused only through `verified_existing_identity` evidence. The source and target user fingerprints, target ID, active source membership, tenant scope, both snapshot fingerprints, independent review, and explicit `preserve_target` credential / `no_import` global-role policies must match. The planner never copies a source password hash or grants a global role. A normal or unverified mapping to the protected user remains blocked. Password recovery and verification tokens are outside this mapping.

The source workspace historically identified as the original Super Admin placeholder is classified as a **candidate**. Preserve it by default. A missing Settings row remains absent; never synthesize one. An exclusion decision can be considered only with a full 19-table tenant dependency inventory, zero memberships/media/API consumers/comments/logs and other tenant-owned rows, a hashed evidence-file `placeholderDependencyAudit` covering all 19 entities plus zero reviewed external integrations/API consumers, and separate approval. The previously observed active membership prevents exclusion until reconciled; no function deletes a record.

Media records, nested image URLs, and CTA/navigation links are distinct. `backend/migration/legacyPreservation.js` reports opaque IDs and provider classes without URLs. A Google Drive or Cloudinary reference is not presumed broken. Availability, ownership, and mapping must be reviewed before any future CDN transfer or URL rewrite. The read-only `database/audit/foundation-5a-legacy-assets.sql` returns aggregate provider/JSON-reference counts from Aiven; it does not export URLs or content.

## First disposable rehearsal

1. Confirm an administrator-approved **separate, disposable database** can be provisioned. Never use Aiven `defaultdb`, the existing Kroombox `uniin_universe`, or a database served by tenant websites. If Kroombox cannot provide a separate database, use an approved isolated MySQL instance or defer the rehearsal. Do not truncate development.
2. Verify current source and target backups and test restoration. Provision the rehearsal schema from the reviewed Kroombox structure and safe administrative bootstrap only. Use separate credentials and network access. Keep the rehearsal backend private; disable outbound SMTP/Brevo, notification delivery, scheduled jobs, webhooks, CDN writes/deletes, and public tenant routes. Do not reuse production CDN write credentials.
3. Collect fresh exact counts, FK actions, orphan/unique checks, and the aggregate asset audit using the read-only Foundation 4/5A SQL. Keep protected identity inventories and HMAC keys outside Git. Prepare complete source-to-target IDs and document source/target collation collisions. The `--legacy-inventory`, `--legacy-decisions`, and `--legacy-api-observations` options of `backend/migration/cli.cjs` accept local JSON; their outputs never contain raw slugs or URLs.
4. Review all 19-table dependencies. Preserve the target Super Admin and its credentials, tenant memberships and roles, API-key **values and ownership**, optional Settings absence, Pages/Posts identities and statuses, legacy JSON and ordering, and media/CDN references. Compare public list/detail, settings/footer, navigation, publication filtering, and the Legacy API v1 contract on an isolated backend after any later approved import.
5. A future operational SQL package needs an independent administrator review. The administrator alone executes it through phpMyAdmin **on the disposable database**. This phase does not generate import DML. After each dependency stage, record counts, mapping coverage, and FK/unique checks before proceeding. On failure, stop; preserve logs/evidence and restore or discard the disposable database.

## Future SQL package design

The future package should have a batch ID and source snapshot fingerprint; explicit source-to-target IDs for all 19 legacy tables; a protected mapping for the existing Super Admin; dependency-ordered stages; preflight collision checks under the target collation; approved slug decisions; and separate checks for optional Settings, JSON references, media IDs, and URLs. Each stage should compare expected row counts and existing mapping rows before any insert. Repeating a stage must detect an already-applied batch and halt for reconciliation rather than silently overwrite or duplicate records. Partial failure needs a recorded checkpoint, exact postflight counts, and a restore plan. Operational DML and any source-row-bearing SQL must be produced locally from authorized protected files in a later phase and reviewed separately. No automatic SQL executor or production cutover is part of Foundation 5A.
