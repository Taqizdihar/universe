# Foundation 3 offline rehearsal preparation

The comparison summary supplied for this phase reports 19 source tables, 140 matching legacy columns, 48 matching index entries, 62 column collation differences, two redundant source `tenant_users` foreign keys, and nine extra target tables. The underlying machine-readable comparison report and complete 19-table roster were not supplied with the prompt. These counts are recorded as administrator findings, **not independently reproduced by this repository**. Source foreign-key actions are missing. The schema validator therefore cannot mark the actual comparison ready until those metadata are supplied.

`backend/migration/schemaMapping.js` compares normalized table, column, index, foreign-key, and collation metadata offline. A caller must provide both inventories with each column's type, nullability, default, ordinal, and collation; each index's ordered columns and primary/unique flags; and each foreign key's ordered columns, referenced table/columns, `onDelete`, and `onUpdate`. Missing critical metadata blocks readiness. A collation difference requires transformation review because distinct source values may compare equal under the target collation. A duplicate foreign key is reported for review. A compatible extra target table does not imply that its data should be imported.

`backend/migration/rehearsal.js` accepts a sanitized 19-table source roster, both schema inventories, source/target data inventories, explicit identity mappings, and validation outcomes. It runs the schema comparison itself before producing an offline dependency order and a go/no-go report. Inventories contain IDs and non-reversible fingerprints of normalized emails and API keys, never raw keys, emails, password hashes, content, or tokens. Fingerprints must use the same normalization and a protected, keyed digest across both inventories; the key stays outside repository and reports. A report remains no-go on incomplete mappings, collisions, orphaned content, missing references, nested media references needing review, or unverified validation. `super_admin_verifications`, `account_auth_state`, and `password_reset_tokens` are excluded from transfer; global roles require separate human review. The actual legacy table roster determines which 19 tables are planned.

## Administrator sequence

1. Keep the active Aiven and Kroombox databases unchanged. Provision a separate **disposable** rehearsal database through an approved administration process; verify a restorable backup and its identity. This repository does not provision databases or import data.
2. Export read-only schema metadata from Aiven and Kroombox using `database/audit/aiven-v2-schema.sql` and `database/audit/kroombox-target-schema.sql`. Run `database/audit/foreign-key-actions.sql` in each database to obtain `ON DELETE` and `ON UPDATE`. Confirm all 19 source table names and the reported counts. Keep actual tenant rows and secrets outside the repository.
3. Compare the inventories offline. Investigate every blocking or review finding, especially the 62 reported collation differences and two redundant foreign keys. Check whether normalized emails, subdomains, and slugs collide under the target collation; determine explicit transformations before rehearsal. Never infer data safety from schema equality.
4. Prepare sanitized inventories and explicit source-to-target IDs. Preserve tenant membership roles, API-key values and ownership, password-hash compatibility, slugs, status, settings/footer, navigation, legacy JSON shape, and CDN references. Verify nested media separately; do not treat CTA or navigation URLs as files. Keep target Super Admin and new authentication tables intact.
5. Generate the offline dependency and readiness reports. Record passing results for identity mapping, memberships, API-key ownership, password-hash compatibility, legacy content round trips, publication status, Legacy API v1, media references, collation collisions, and backup/rollback. Review all findings and record an approved mapping plan. A future operational DML package requires **separate** administrator review and approval. This phase supplies no import SQL or execution tool.
6. The administrator alone may execute reviewed DDL/DML through Kroombox phpMyAdmin **in the disposable rehearsal database**. Run read-only preflight and postflight counts, FK/orphan checks, tenant isolation checks, published/draft checks, and the existing Legacy API v1 contract tests against a rehearsal backend. Compare Pages, Posts, Settings, Navigation, and media behavior using synthetic or approved test data.
7. Go only when schema metadata is complete, collation collisions are resolved, all identity/ownership checks pass, API v1 output remains compatible, CDN assets remain accessible, and a restorable backup plus cutover/rollback procedure are approved. Otherwise record no-go, do not cut over API base URLs, and reconcile the disposable rehearsal database from its backup or discard it after review.

## Hosting boundaries

Database migration moves records; it does not move existing websites' API base URLs. An `x-api-key` still identifies an active tenant and public Pages/Posts/Settings/Navigation remain tenant-scoped and publication-filtered under Legacy API v1. Existing sites that call Render continue to call Render until an explicitly managed API base-URL cutover. CDN asset migration is separate from both database migration and API cutover; preserve valid media URLs or plan a reviewed rewrite after asset verification. The future Content Schema Registry is a separate project and is not activated here. No endpoint, redirect, or tenant integration changes are part of Foundation 3.
